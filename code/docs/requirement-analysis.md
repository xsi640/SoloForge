# 需求分析：团队任务看板应用

## 1. 项目概述

做一个面向小团队的 Web 看板应用，用于解决团队成员的任务跟踪问题。

- 项目要做什么：提供一个可以把任务记录下来的看板，任务以卡片形式存在，通过状态列体现当前进度，成员在同一处查看和更新任务。
- 核心方向：任务的可记录、可跟踪、可检索、可提醒。
- 一句话定位：一个部署在内网、供 10 人左右小团队统一记录和跟踪任务的轻量看板应用。

## 2. 目标用户

- 主要使用者：10 人左右的小团队成员，人人可直接访问和编辑，不区分角色权限。
- 使用场景：通过内网浏览器访问应用，创建任务、查看当前工作分布、拖动卡片更新任务状态、按条件查找任务。
- 用户具备的前提条件：处于同一内网环境，能通过 IP 访问服务器，使用浏览器操作，并持有管理员分配的登录账号。

## 3. 要解决的问题

- 当前痛点：任务没有统一的记录载体，只能靠口头或群聊同步，任务容易被遗漏，进度不透明，无法跟踪一个任务从创建到完成的完整过程。
- 为什么值得解决：只要任务先被稳定记录下来，进度就不再依赖反复沟通；团队能看到每个人手上的工作与整体状态，减少遗漏和重复确认。

## 4. 需求目标

- 任务可创建：成员能把任务记录到看板中，附带标题、负责人、状态、截止日期、优先级和描述，用户获得的是一个不会丢失的任务清单。
- 任务可维护：创建后能编辑和删除，用户获得的是可持续修正的任务信息，而不是一次性录入的死数据。
- 状态可见可流转：任务以卡片形式分布在状态列中，支持拖动卡片切换状态，用户获得的是直观的进度视图。
- 任务可检索：支持搜索和筛选，用户获得的是在任务量增长后仍能快速定位目标任务的能力。
- 到期有提醒：临近或超过截止日期时给出提醒，用户获得的是对时间节点的主动感知，而不是靠人工盯日期。
- 统一入口：成员登录后进入同一个看板，用户获得的是一个团队共享的单一信息源。

## 5. 模块边界说明

| 模块 | 职责 |
|---|---|
| 账号与登录 | 管理账号来源、身份认证与账号生命周期；管理员可在应用内新增成员、重置密码、停用或启用成员，成员登录后进入看板 |
| 看板管理 | 维护唯一的项目看板本身 |
| 列管理 | 定义看板的状态列及其顺序 |
| 任务卡片 | 管理任务的业务字段：标题、负责人、状态、截止日期、优先级、描述 |
| 看板视图 | 展示列与卡片，处理拖动卡片换列换状态 |
| 检索 | 对任务进行搜索与筛选 |
| 提醒通知 | 按截止日期触发站内提醒并触达用户 |

边界规则：

- 任务字段的增删改归「任务卡片」；由拖动引起的状态变化归「看板视图」触发，但状态字段以「任务卡片」为唯一数据归属，避免两处各自维护状态。
- 状态列的定义与顺序归「列管理」，不属于「看板管理」。
- 截止日期字段本身归「任务卡片」，基于截止日期的触发规则与提醒触达归「提醒通知」。
- 搜索与筛选归「检索」，看板视图不承担查询逻辑。
- 登录相关的一切归「账号与登录」，其他模块不重复实现身份判断。

合并、拆分或排除的模块及原因：

- 评论、附件、子任务、标签：明确排除，本期不做。
- 甘特图、统计报表：明确排除，本期不做。
- 归档能力：排除，不做看板与任务的归档。
- 多项目管理：排除，本期全局只有一个项目对应一个看板。
- 角色与权限模块：排除，不做权限区分，登录后成员对看板与任务的权限一致；管理员身份仅作为成员管理入口存在，不产生任务层面的权限分级。

## 6. 成功标准

- 用户在完成后能做到：登录后看到团队全部任务及其负责人、状态和截止日期；拖动卡片即可更新任务状态；能按条件搜到目标任务；到期任务会收到提醒。
- 判断需求完成的可验证标准：
  - 任意成员都能在同一个看板中看到所有任务，不需要再靠口头或群聊同步进度。
  - 一个任务从创建、修改、换状态到完成的全过程都能在应用中被查到。
  - 搜索和筛选能在任务列表中准确命中目标任务。
  - 临近或超过截止日期的任务会产生站内提醒。

## 7. 范围与边界

必做：

- 账号与登录：管理员在应用内预先创建账号，成员使用账号密码登录，不做自助注册；成员管理包含新增成员、重置密码、停用与启用，不做成员删除。
- 看板：单一项目看板，内网通过 IP 直接访问，不要求 HTTPS。
- 状态列：固定三列「待办 / 进行中 / 完成」，不支持自定义列。
- 任务卡片：标题、负责人、状态、截止日期、优先级、描述；支持新建、编辑、删除。
- 看板视图：卡片在列中展示，支持拖动卡片切换状态。
- 检索：支持搜索与筛选。
- 提醒：站内提醒，登录后在应用内可见。

暂不做：

- 评论、附件、子任务、标签
- 甘特图与统计报表
- 看板与任务的归档
- 多项目、多看板切换
- 角色与权限区分
- 自助注册
- 邮件、企业微信、钉钉等外部提醒通道
- 自定义状态列
- HTTPS 与公网访问

## 8. 约束与风险

主要限制：

- 部署环境：内网 Linux 服务器，通过 IP 直接访问，不依赖公网与外部服务。
- 技术栈：前端 Vue，后端 Java，数据库 H2（嵌入式文件模式）。
- 权限模型：不区分角色，登录即具备全部操作权限。
- 提醒通道：受内网环境限制，仅站内提醒，不接外部消息服务。

主要风险：

- 并发写入：10 人同时拖动卡片可能触发写锁等待。原计划使用 SQLite 并接受该限制，阶段 3A 评估后改为 H2 嵌入式文件模式，见 U-09。
- 业务层面的其他风险：用户明确表示暂未识别出其他业务风险。

## 10. 人工确认结论

- 用户已确认的内容：目标用户为 10 人左右小团队；形态为 Web 应用；一个项目一个看板；不分权限；任务字段为标题、负责人、状态、截止日期、优先级、描述；拖拽、编辑删除、搜索筛选、提醒、登录均纳入本次范围；部署到内网 Linux，技术栈为 Vue + Java + SQLite；成功标准为团队能在同一处看到任务并与状态保持同步。
- 明确延期的事项及后续处理方式：U-04（SQLite 并发写入限制）已在阶段 3A 评估并关闭，结论见 U-09：数据库从 SQLite 更换为 H2，原并发限制不再适用。
- 阶段 3A 补充记录：技术栈由「Vue + Java + SQLite」修订为「Vue + Java + H2」，见 U-09；其余需求范围、模块边界与成功标准不变。
- 阶段 2A 补充记录：U-08 在阶段 2A 交互中新增并确认，用于把「账号由服务器侧初始化」修订为「管理员在应用内管理账号」，需求范围以本节为准。
- 阶段完成判断：目标用户明确，问题清晰，需求目标明确，成功标准可验证，范围与边界清楚，主要限制和风险已说明，全部未确定事项已确认、排除或明确延期，阶段 1 完成，可进入阶段 2 产品设计。
