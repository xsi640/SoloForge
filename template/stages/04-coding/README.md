# 阶段 4：代码实现阶段

## 阶段目标

按已定稿的任务文档与 API 文档实现代码，边实现边更新任务状态，并留下可追溯的实现与验证记录。

```text
读取已定稿的 03-tasks.md 和 03-api-design.md
→ 确认实现方式（串行或并行）
→ 按任务顺序实现并更新任务状态
→ 生成 04-implementation-record.md
→ 执行端到端验证
→ 用户确认
```

编码与文档分开：阶段 3 的文档未定稿不得开工。发现文档问题先改文档，再改代码。

## 目标

按已定稿的 `03-tasks.md` 与 `03-api-design.md` 实现代码，并保证实现与文档一致。

阶段 4 关注：

- 按已确认的任务顺序实现代码
- 任务状态跟踪

- 实现记录与端到端验证证据

阶段 4 不关注：

- 重新做技术选型

- 任务范围或验收标准的调整
- 已定稿的接口与字段的修改
- 用户流程和交互逻辑变更
- 视觉样式设计

## 交互流程

### 第 1 步：读取任务文档和 API 文档

AI 读取 `03-tasks.md` 和 `03-api-design.md`，总结任务清单、依赖、并行分组、最小可运行闭环与接口定义。如果两份文档未定稿，或仍有未处理的 `TASK-TBD-###`，不能开始阶段 4。

### 第 2 步：确认实现方式

和你确认串行实现还是并行实现。任务较少、耦合较紧时按任务顺序串行推进；任务数量较多（经验值 10 个以上）且依赖与并行分组清晰时，按 [SKILL.md](SKILL.md) 的并行方式：先冻结契约，再按模块交给多个 AI 子代理并行实现，由协调者统一完成集成与端到端验证。

### 第 3 步：按任务顺序实现

按已确认的顺序推进，不擅自扩大范围；严格遵守 `03-api-design.md` 的接口与字段；每完成一个任务就更新状态和实际产出。发现架构不可行时回到阶段 3A，发现任务或接口定义问题时回到阶段 3B，发现需求或交互问题时回到对应阶段，不要在实现里静默改掉。

### 第 4 步：记录实现过程

实现过程中同步维护：

```text
docs/04-implementation-record.md
```

记录实际执行方式（串行或并行、批次与写入范围）、集成阶段发现的缺陷与修复、验证证据，以及明确的未验证项。

### 第 5 步：端到端验证

编译通过不等于能运行。真实启动应用并执行可重复运行的端到端验证，至少覆盖鉴权边界、参数校验、状态派生、错误码、写操作一致性与重复启动幂等性。未做浏览器端与真机验证的部分，明确列为未验证项，交由阶段 5 覆盖。

### 第 6 步：收尾与定稿

你确认后，任务状态全部回填到 `03-tasks.md`，临时产物清理，`04-implementation-record.md` 定稿。

## 并行实现方式

任务数量较多时，阶段 4 可采用「协调者 + 多个并行子代理」的方式，核心约束是：

- 协调者先一次性冻结契约层（schema、实体、DTO/VO、枚举、接口、公共层），再分派子代理；
- 一个模块只交给一个代理，模块边界即写入边界，共享文件一律由协调者持有；
- 前端父子组件的 props / emits 必须先冻结成文字契约；
- 子代理只对「自己的文件能编译」负责，跨模块集成与端到端验证必须由协调者承担；
- 子代理发现契约问题只能上报，不能自行修改。

完整原则、执行流程、集成阶段常见缺陷与子代理任务书模板见 [SKILL.md](SKILL.md) 与 [templates/agent-task-brief.md](templates/agent-task-brief.md)。

## 编号规则

阶段 4 不新增编号体系，直接复用阶段 3B 的 `TASK-###` 与 `API-###`；实现记录中发现的缺陷使用 `D-###`。

## 阶段 4 约束

不能修改已确认的需求、UX、UI 和已定稿的接口与任务定义：

- 发现需求问题 → 回到阶段 1
- 发现交互问题 → 回到阶段 2A
- 发现视觉问题 → 回到阶段 2B
- 发现架构问题 → 回到阶段 3A
- 发现任务或接口定义问题 → 回到阶段 3B

编码（阶段 4）与文档（阶段 3）分开：文档未定稿不得开工，发现文档问题先改文档再改代码。
