# 阶段 3：代码设计阶段

## 阶段目标

阶段 3 分为两个严格有先后关系的步骤：先定架构，再写文档。代码实现属于阶段 4。

```text
阶段 3A：技术架构选型
读取阶段 1 需求分析文档
→ AI 通过 Skill 与用户交互式询问
→ 对比 2~3 个候选架构方案并选定
→ 确定技术栈、分层、模块映射、数据与接口约定
→ 用户确认
→ 生成 03-tech-architecture.md

阶段 3B：任务拆解与文档编写
读取已确认的 03-tech-architecture.md
→ 确认实现顺序和最小可运行闭环
→ 逐模块拆解任务并明确依赖
→ 生成 03-tasks.md 和 03-api-design.md
→ 定稿任务文档与 API 文档
```

技术架构选型是代码设计阶段的前置步骤。没有确认的 `03-tech-architecture.md`，不允许开始拆解任务与编写任务文档和 API 文档。

两步严格有先后关系：3B 必须在 `03-tech-architecture.md` 确认后才能开始。两份文档定稿后，才进入阶段 4 编码。编写文档与写代码分开，便于在动手前把任务、接口和验收标准一次确认清楚。

## 固定文件

阶段 1 输入：

阶段 2 参考输入（可选）：

阶段 3 Skill：


阶段 3A 输出：

```text

```

```text

docs/03-api-design.md
```

当前不需要用户填写任何模板。上述文档均由 AI 按 Skill 通过交互式问答生成。

阶段 3 的产物到 `03-api-design.md` 为止；`docs/04-implementation-record.md` 与代码由阶段 4 产出，见 [阶段 4：代码实现阶段](../04-coding/README.md)。

如果 `01-requirement-analysis.md` 不存在，或阶段 1 仍有未处理的未确定事项，应先回到阶段 1。

# 阶段 3A：技术架构选型

## 目标

先回答“用什么做、怎么划分、怎么跑起来”，再进入任务拆解和编码。技术架构文档是阶段 3B 的唯一架构输入。

架构阶段关注：

- 交付形态与运行环境
- 架构风格与系统分层
- 技术栈选型与版本约束
- 需求模块到代码模块的映射
- 数据结构与存储设计
- 接口风格与鉴权约定
- 工程结构与配置管理
- 非功能性要求（性能、可靠性、安全、成本）
- 构建、运行与部署方式
- 选型理由与被放弃的备选方案

架构阶段不关注：

- 业务代码实现
- 单个任务的拆解
- 视觉样式细节
- 需求本身的增删改
- 已确认的用户流程和交互逻辑

## 架构交互流程

### 第 1 步：读取阶段 1 文档

AI 先读取 `01-requirement-analysis.md`，总结交付形态线索、模块边界、成功标准和约束，不要求你重新填写项目背景。

### 第 2 步：分轮询问架构问题

AI 每轮只问少量关键问题，通常围绕：

1. 以什么形态交付，由谁来运行？
2. 有没有必须使用、或者你更熟悉的技术？
3. 部署在哪里，有没有成本、网络或内网限制？
4. 数据量、并发、离线使用或隐私有没有硬要求？
5. 只给一个人用，还是需要多人或多端共同使用？
6. 你打算怎么长期维护它？

### 第 3 步：给出候选方案并选定

AI 必须先给出 2~3 个候选方案，说明每个方案适合的场景和需要付出的代价，再给出推荐和理由，由你拍板。选定结果记录为架构决策（`ADR-###`）。

### 第 4 步：建立架构设计

选定方案后，逐项确定技术栈、系统分层、模块映射、数据实体、接口约定、工程结构和部署方式。技术栈必须写明确切的版本要求。

### 第 5 步：自查并逐项确认

AI 主动检查架构与需求是否一致、是否过度设计、每个选型是否有理由、需求模块是否全部覆盖，把发现的问题分为“必须澄清”和“建议补充”后逐条和你确认。

### 第 6 步：处理待确认事项并生成文档

所有 `ARCH-TBD-###` 逐项处理为确认、排除、延后或继续追问。你最终确认后生成：

```text
docs/03-tech-architecture.md
```

## 技术架构文档结构

最终文档至少包含：

1. 架构目标与约束（含非功能性约束）
2. 交付形态与运行环境
3. 技术栈与分层
4. 模块划分与需求模块映射
5. 数据与存储
6. 接口约定
7. 构建、运行与部署
8. 架构决策记录
9. 技术风险
10. 待确认事项处理结果
11. 人工确认结论

## 编号规则

| 对象 | 编号格式 | 示例 |
|---|---|---|
| 架构决策 | `ADR-###` | `ADR-001` |
| 代码模块 | `MODULE-###` | `MODULE-001` |
| 待确认事项 | `ARCH-TBD-###` | `ARCH-TBD-001` |

只给真正需要被后续引用的对象编号。需求文档中的模块名称必须原样复用，不得在架构阶段重新命名。

# 阶段 3B：任务拆解与文档编写

## 目标

把已确认的架构拆成可独立执行、可验证、可跟踪的任务，并同步产出 API 文档。本阶段只产出文档，不写代码。

3B 关注：

- 实现顺序与最小可运行闭环
- 任务拆解、依赖关系与并行分组
- 每个任务的验收标准
- 任务文档 `03-tasks.md`
- API 文档 `03-api-design.md`

3B 不关注：

- 重新做技术选型
- 需求变更
- 用户流程和交互逻辑变更
- 视觉样式设计
- 编写业务代码（属于阶段 4）

## 3B 交互流程

### 第 1 步：读取技术架构文档

AI 读取 `03-tech-architecture.md`，总结分层、模块清单、数据实体、接口约定和构建运行方式。如果仍有未处理的 `ARCH-TBD-###`，不能开始 3B。

### 第 2 步：确认实现顺序

和你确认先做哪个模块、哪个组合构成“能跑起来的最小闭环”、哪些现在不做。默认先打通最小闭环，再扩展功能。

### 第 3 步：逐模块拆解任务

按 `MODULE-###` 逐模块拆任务，每个任务必须可独立执行、有明确的输入和产出、有可验证的验收标准、写明依赖项。

### 第 4 步：确认依赖与并行分组

标出每个任务的依赖项、可以并行执行的任务，以及位于关键路径上的任务。

### 第 5 步：生成任务文档和 API 文档

生成：

```text
docs/03-tasks.md
docs/03-api-design.md
```

### 第 6 步：处理待确认事项并定稿

逐项处理全部 `TASK-TBD-###`，过程中新增的事项同样加入列表。你确认后，任务文档和 API 文档定稿。

定稿的 `03-tasks.md` 与 `03-api-design.md` 是阶段 4 实现代码的唯一输入，也是阶段 5 测试阶段的输入。

## 任务文档结构

`03-tasks.md` 至少包含：实现范围与顺序说明、任务清单、任务依赖与并行分组、任务进度状态汇总、待确认事项处理结果、人工确认结论。

任务清单示例：

| 任务编号 | 任务名称 | 模块 | 依赖项 | 验收标准 | 状态 |
|---|---|---|---|---|---|
| TASK-001 |  | MODULE-001 | 无 |  | 待处理 |

「模块」列填 `MODULE-###`，公共基础设施任务填「公共」。任务状态只能取以下值：待处理 / 进行中 / 待验证 / 已完成 / 已阻塞。标记为「已阻塞」时，在表下方说明原因和解除条件。

## API 文档结构

`03-api-design.md` 至少包含：接口约定、接口清单、数据结构、错误与异常约定、待确认事项处理结果。

接口不限于 HTTP。有远端服务时记录协议、路径、鉴权和错误码；本地应用记录服务层和仓储层的方法；确实没有接口时直接写明「本项目无外部接口」并说明原因。

## 编号规则

| 对象 | 编号格式 | 示例 |
|---|---|---|
| 任务 | `TASK-###` | `TASK-001` |
| 接口 | `API-###` | `API-001` |
| 待确认事项 | `TASK-TBD-###` | `TASK-TBD-001` |

任务文档必须复用架构文档中的 `MODULE-###` 编号，不得重新编号。3B 只保留一个待确认清单，编号为 `TASK-TBD-###`。

## 阶段 3 约束

代码设计阶段不能修改已确认的需求、UX 和 UI：

- 发现需求问题 → 回到阶段 1
- 发现交互问题 → 回到阶段 2A
- 发现视觉问题 → 回到阶段 2B
- 发现架构问题 → 回到阶段 3A

编写文档（阶段 3）与实现代码（阶段 4）分开：文档未定稿不得开工，发现文档问题先改文档再改代码。

## 下一步

阶段 3 完成后，进入：

- 阶段 4：代码实现阶段

阶段 4 会读取已定稿的 `03-tasks.md` 和 `03-api-design.md` 实现代码，见 [阶段 4：代码实现阶段](../04-coding/README.md)。阶段 5 测试阶段同样读取这两份文档作为测试输入。
