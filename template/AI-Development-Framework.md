# SoloForge AI时代软件开发工作方法（单人版）

> 版本：0.5  
> 日期：2026-09-17  
> 目标：建立一套简单、可复用、适合一个人长期坚持的 AI 时代软件开发方法。

## 1. 总体目标

SoloForge 的目标不是让 AI 替代开发者，而是让 AI 变成一个实用的“扩展能力层”，帮助你在以下方面提升效率：

- 需求分析与任务拆解
- 产品设计与交互表达
- 技术架构选型与技术栈决策
- 编码、测试与文档整理
- 发布前检查与复盘

最终目标是：在不追求复杂流程的前提下，形成一个简单、可执行、可持续迭代的开发方法。

---

## 2. 工作顺序

### 阶段 1：需求分析阶段
目的：把模糊想法变成明确开发目标。

人的工作：

- 明确要解决的问题
- 确定目标用户和核心价值
- 设定成功标准
- 审核 AI 生成的需求草案
- 确认需求边界与优先级

AI 可以协助：

- 扩展需求描述
- 提炼关键价值点
- 列出风险和边界
- 生成简版需求文档

输出：

- 需求说明
- 目标用户
- 关键价值点
- 成功标准

---

### 阶段 2：产品设计与 UI/UX 设计
目的：先明确“做成什么样”，再开始开发。

人的工作：

- 确认核心功能和页面主流程
- 设计或调整 UI/UX 草图与交互方式
- 审核 AI 生成的页面结构说明
- 确认先做什么、后做什么

AI 可以协助：

- 生成页面结构草案
- 生成交互流程说明
- 列出页面状态与异常状态
- 产出可执行的设计说明

输出：

- 产品设计说明
- 页面结构与功能流程
- UI/UX 草图或界面说明
- 关键交互行为
- 页面状态说明

---

### 阶段 3：代码设计阶段
目的：先把技术架构选型定下来，再把设计拆成任务与接口文档。代码设计阶段分 3A、3B 两步，严格有先后关系；文档定稿后才进入阶段 4 编码。

人的工作：

- 确认交付形态、技术栈和维护方式
- 审核候选架构方案的取舍对比，并选定方案
- 审核数据结构和任务拆解结果
- 确认任务文档与 API 文档定稿

AI 可以协助：

- 对比候选架构方案的优缺点和代价
- 生成技术架构文档草案
- 生成 API 文档草案
- 自动拆分任务文档
- 汇总待确认事项与风险
- 生成文档摘要

输出：

- 技术架构文档
- API 文档
- 任务文档

---

### 阶段 4：代码实现阶段
目的：按已定稿的任务文档与 API 文档实现代码，并留下可追溯的实现与验证记录。

人的工作：

- 确认实现方式（串行或并行）
- 跟踪任务进度
- 对 AI 生成代码做校验和必要修正
- 验收实现结果与端到端验证证据

AI 可以协助：

- 生成代码骨架
- 切分并行开发的契约层与模块边界
- 记录实现过程与集成缺陷
- 汇总任务进度与风险
- 编写端到端验证脚本

输出：

- 代码实现
- 实现记录
- 任务进度状态

---

### 阶段 5：测试阶段
目的：确保功能可用，并尽早发现问题。

人的工作：

- 制定测试重点和关键路径
- 进行人工测试
- 验证 AI 生成的测试用例是否覆盖正确场景
- 修复发现的问题并重新验证

AI 可以协助：

- 生成测试用例
- 检查边界条件
- 汇总测试结果
- 识别潜在遗漏项

输出：

- 测试计划
- 功能测试清单
- 测试记录
- 已修复与待修复问题列表

---

### 阶段 6：发布阶段
目的：把开发完成的内容整理成可交付结果。

人的工作：

- 确认发布内容和发布时间点
- 检查编译、部署、配置和回滚是否齐全
- 审核发布说明与风险提示
- 发布后进行验证

AI 可以协助：

- 生成发布说明
- 提供回滚建议
- 检查发布前遗漏项

输出：

- 编译产物
- 部署包
- 发布说明
- 回滚方案
- 发布后检查清单

---

## 3. 可直接使用的工作原则

1. 一次只做一个明确任务，不要一次性做大块改造。
2. 先做最重要的功能，再扩展细节。
3. 每个阶段都要有明确输出，不写“看起来没问题”的空文档。
4. AI 负责扩展思维、生成草案、整理信息和重复劳动。
5. 你负责判断、审批和最终交付。
6. 保留必要文档，避免文档堆积。

> 结论：最重要的是简单、明确、可验证，而不是复杂、全面、完美。

---

## 4. 每个阶段至少保留的“必要文档”

- 需求分析：目标、用户、价值、验收标准
- 产品/UI：页面结构、关键交互、状态说明
- 代码设计：技术架构文档、API、任务文档
- 代码实现：实现记录、进度状态
- 测试：测试清单、问题记录
- 发布：发布说明、回滚方案、验证记录

各阶段的过程文档统一放在项目根目录下的 `docs/` 目录中（阶段 4 的 `04-implementation-record.md` 也在其中），直接放在 `docs/` 根层，不再按阶段建子目录；文件名以阶段编号开头（如 `01-requirement-analysis.md`、`03-tasks.md`、`05-test-record.md`），具体名称与各阶段 README / SKILL 的「固定文件」一节保持一致；阶段 2B 的设计图放在 `docs/design/` 子目录，文件名以 `UI-###` 编号开头（如 `UI-001-login.png`）；阶段 4 生成的代码放在项目根目录下，编译产物与部署包不放进 `docs/`。

这样可以保证：

- 文档不是为了写而写；
- 文档是为了后续执行、测试、发布和维护。

## 5. AI 的使用边界

AI 适合做的事情：

- 把想法扩展成更完整的需求
- 生成产品结构说明
- 对比技术架构方案并梳理技术栈
- 产出 API 文档草案
- 拆解任务并生成任务文档
- 生成测试用例与测试建议
- 汇总问题与生成发布说明

AI 不应该做的事情：

- 独自决定关键业务行为
- 绕过人工审查
- 无约束地修改生产环境配置
- 擅自发布高风险变更

必须遵守的原则：

- 关键决策由你自己负责
- 高风险修改必须人工确认
- AI 的输出必须能被解释、审查和回溯

---

## 6. 推荐落地方式

1. 先做需求分析，明确目标和验收标准。
2. 再做产品设计，用页面结构和交互说明锁定方向。
3. 接着做代码设计阶段：先完成技术架构选型，再形成并定稿 API 和任务文档。
4. 然后进入代码实现阶段：按文档实现代码，记录实现过程并做端到端验证。
5. 再做测试阶段，做关键路径验证和问题记录。
6. 最后进行发布，做构建、检查、说明和回滚准备。

---

## 7. 成功标准

一个稳定可用的 SoloForge 工作方法，至少应该满足：

- 每个阶段都有明确输出
- 每个任务都有状态记录
- 关键问题都有修复与回归记录
- 发布前有检查清单
- 每次迭代后都有可复盘内容
